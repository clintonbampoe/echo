# Getting Started with Echo API

**Written by:** @clintonbampoe
**Last updated:** 2026-07-31 by @clintonbampoe

This is your entry point if you are setting up Echo locally for the first time. The main [Api Usage](./ApiUsage.md) guide assumes you already have a valid JWT token. However, Echo is a multi-tenant system. This means that, every user (including Admins) must belong to a Congregation.

This guide walks you through the mandatory two-step process to create your first valid credentials.

---

## Creating a new user account

**Admins cannot exist alone.** The `User` table in `Echo` has a required foreign key (`CongregationId`) enforced at both the database and validation levels.
This means that a `User` account has to been attached to a congregation as a requirement.

Due to this constraint, there are two ways of creating an account in **Echo**

1. **Registering as a admin of a  new congregation**:
   This is the simplest way to get started. The backend handles everything in a single database transaction. Either the Admin account and Congregation are created successfully or they both gracefully fail. This keeps our data integrity and makes sure there are no orphaned **Congregations** or **Admin** accounts.

2. **Signing up as part of an existing congregation with an Invitation Token**:
   If you have the permission of the admin of an existing congregation, you can retrieve an **Invitation Token** from them and Sign up with that token. This way, the system would attach you to whatever congregation that token was generated from.

## Registering as a new congregation admin

This is the simplest way to get started. The backend handles everything in a single database transaction and rollback cleanly if it encounters any errors.

**Endpoint:** `POST /api/auth/v1/register/congregation`
_This is a public endpoint. No authentication required_

**Payload**

```json
{
  "congregationDto": {
    "name": "",
    "orgType": "Church",
    "phoneNumber": "",
    "emailAddress": "",
    "postalAddress": "",
    "websiteUrl": "",
    "region": "Ahafo",
    "city": "",
    "town": "",
    "gpsAddress": ""
  },
  "userDto": {
    "name": "",
    "emailAddress": "",
    "password": "",
    "role": "Admin"
  }
}
```

Response returns a **200 OK** with your `UserId`. `CongregationId` is created but not returned for security.

## Signing up with an invitation token

You can also retrieve an **Invitation Token** generated by the Admin of an existing congregation and register with the token. This would attach your `User` account to that specific congregation.

**Endpoint**: `POST /api/auth/v1/register/member`

**Payload**

```json
{
  "token": "",
  "name": "",
  "email": "",
  "password": ""
}
```

>**Note:** This is the primary way of adding **Congregation Staff** and **Users** to a specific congregation. The `Role` of the account created is determined from the type of **Invitation Token** created.

## Verifying your Account

After your `User` account is created. You won't be able to login until you verify the account. The endpoint accepts the email attached the your account as the payload.

**Endpoint**: `POST /api/auth/v1/verify/account`

**Payload**

```json
{
"email": "clintbamp@gmail.com"
}
```

> **NB:** this endpoint returns the account verification token as a response. This isn't supposed to be the usual response. The token is supposed to be sent to the email registered with the `User` account. However, because we've not bought our own domain yet, we can only send emails to the address I used
> to register the resend account `clintbamp@gmail.com`.
>
> This implies that, any other `User` account you create with a different email would throw an exception. Hence, the token is returned here so that we
> won't have to keep forwarding messages from my inbox.
>
> This would be corrected as soon as we purchase our own domain and register our email subdomain into Resend.

**Response**

```json
{
  "message": "Operation Completed Successfully. Token: 35p7O2pX8RVnzmEK4btktg"
}
```

To complete your `User` account verification, take the token and attach it as a payload to the verify-email endpoint

**Endpoint**: `/api/auth/v1/verifications/verify-email?token=####`
where `####` represents the token

If the token is valid, congratulations you've successfully verified your account.

> **NB** Most of these steps are going to be automated on the client side to streamline user experience. The architectural designs behind this flow is intentional and was made to prioritize modularity and support for multiple clients at the same time.

## Authenticating and acquiring a JWT token

With your `User` account now verified, you can now access the protected endpoints by acquiring a JWT token which you can attach to every request to access such endpoints.

See [Acquiring a JWT Token](./ApiUsage.md#authentication) for more details on this.
